With the stack proven, the work I’m most invested in: long-context memory. These tasks aren’t Markovian — the current frame alone doesn’t determine the right action. Long context is what makes a policy reactive: it acts on what has already happened, not just what it sees right now.

01

Setup & data

Before a policy learns anything, the system has to be right: synchronized data, the correct control behavior, and a real-time loop to run it all.

01.a

Latency compensation

Multiple cameras arrive out of phase, and the robot’s state runs on its own clock. Everything has to be aligned to one timeline before the policy sees it.

Read moreRead less

The streams come in at different rates and delays. I re-express the query time in the cameras’ own timebase and back off half a frame, so every camera lands within half a frame of one shared observation timestamp — and the policy never trains or acts on a temporally inconsistent view.

Choosing the observation time

Two corrections to the poll time — shift into the hardware-timestamp timebase, then back off half a frame — keep every camera within half a frame of a shared observation timestamp.

01.b

Control

Three things matter more than people expect: gains, compliance, and frequency.

Read moreRead less

Gains. Tracking stiffness sets what the arm can do and how forgiving it is.

Compliance. A little give keeps contact from turning into a fight — safer for the task and for the hardware.

Frequency. The rate you command and record actions shapes the data, and therefore what the policy can learn.

Deployment runs as a receding-horizon (MPC-style) loop: predict an action chunk, execute part of it, then replan from the latest observation.

04

Memory as reactivity

Some tasks can’t be solved from the current frame. Take memory away and a policy breaks in predictable ways — these failure modes are exactly why memory matters.

04.a

Why memory matters: reactivity

Train a memoryless policy on an expert that uses memory, and it breaks in three predictable ways.

Read moreRead less

Unintentional looping. It repeats a sub-step it can’t tell it already did.

Branch selection — “perceptual aliasing.” Two different states look identical, so it picks the wrong branch.

Timing & counts. It can’t wait a set amount of time or do something exactly n times.

All three are the same failure from different angles: the policy can’t separate states that look alike. That framing also explains why a longer execution horizon helps, not just longer context. (Worked out with a collaborator at MIT.)

The intuition Effective memory = context length (true memory) + action horizon.

03

Real-time inference

Inference is usually done a little wrong — and that’s what makes robots jittery. You can’t “plan → wait for the model → execute → plan” when the robot has to keep moving, so the system runs a receding-horizon loop and compensates for the model’s inference delay.

Action-chunk stitching

Each inference predicts a chunk of future actions; only the first steps run before the next chunk is predicted, so consecutive chunks overlap and the controller must blend across the seam to avoid a visible jerk.

03.a

What good evaluation needs

Smooth, reliable real-time behavior comes down to five things.

Read moreRead less

Model confidence. Low-entropy actions come from enough data — and data that’s actually learnable.

Low-level precision. The controller has to execute what the policy asks for, exactly.

Seam smoothing. Real-time chunking and train-time latency compensation, plus clean transitions between chunks.

Low latency. Quantization and compilation, distillation, encoder caching, and fewer denoising steps (e.g., DPM-Solver).

Observation latency. Measure it — then fix it.

Closing the loop

Reinforcement learning

I built the infrastructure to run DPPO and DSRL on diffusion policies. Early days, but promising.

Still fairly untested, but DSRL already showed something interesting: with a reward of −1 per timestep until success and a large penalty on failure, the policy started tightening its control exactly where it mattered — the screw-pick phase.

02.b

Intervention & recovery

A model is only as good as its recovery.

Read moreRead less

Compliant intervention: while the policy runs, a gentle physical nudge can put it back on course. Recovery matters as much as the nominal behavior — it’s where reliability actually lives.

02

Force

A measured take: capturing and measuring force well is genuinely hard, so I treat it as one tool among many — not a cure-all.

Two questions: how to feel force, and how to use it.

Read moreRead less

Feeling it. Getting a clean force signal off real hardware is harder than it sounds — the sensing itself is the bottleneck. I’ve experimented with force feedback using NEXT, the learning-based disturbance observer from the FACTR 2 paper.

Using it as input. It catches contact events that vision and pose miss — but press a little too hard and you’re out of distribution.

Using it as output. Command a target force on an object directly — or let force enter implicitly, through compliance and stiffness.
